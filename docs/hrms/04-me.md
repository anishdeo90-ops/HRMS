# HRMS — Me module (Employee Self-Service)

Captured: 2026-08-08 · batch 2
Tab strip: `My-In-Out` · `Leaves` · `Ranking` · `Bill Reimbursement`

**This is the ESS portal** — every employee logs in and sees their own record here.
Scope is always "my own data"; the manager/HR equivalents live under `Team`.

## 1. My-In-Out

Page title: `My In Out`
Toolbar: `Filter` · `Reset` · `Export CSV`
Sub-tabs: **`Manual In-Out`** (active) · `Multiple Punches`

### Table — Manual In-Out

| Column | Format observed |
|---|---|
| Date | `01-08-2026-Sat` — `DD-MM-YYYY-Ddd`, day name appended |
| In-Time | `00:00` |
| Out-Time | `00:00` |
| Duration | `00:00` |

Rows present for **every calendar day of the month including Saturdays and
Sundays**, all zeroed.

> **Schema consequence — this is not a punch log.** A row exists for each
> employee × each calendar day regardless of whether they punched. So the model
> is a pre-generated **attendance day register** (`attendance_days`), with punches
> attached to it — not a table of punch events that gets grouped by date on read.
>
> That matters because: weekly-offs, holidays and absences need a row to *be*
> marked on, LOP calculation needs a complete date spine, and "Absent: 6" on the
> dashboard is only computable if absent days physically exist as rows.
>
> Implication: a scheduled job materialises the register forward. That is almost
> certainly what **Settings → Cron Master** exists for.

### `Multiple Punches` sub-tab
⬜ not captured. Presumably the raw punch events (multiple in/out pairs per day)
that roll up into the Manual In-Out row. Needs capture before the attendance
schema is fixed — it decides whether `attendance_punches` is a child table.

> the shared approval engine.

## 4. Ranking

Page title: `Your Ranking`. Horizontally scrolling table. `Total Records Count is 0`.

### Columns
`Employee code` · `Employee name` · `Quarter` · `Rank` ·
`Quantity of Work` · `Quality of Work` · `Consistency` · `Mentoring Peers` ·
`Team Player` · `Pro-activeness` · `Conduct` · `Credit Score` ·
`Overall Percentage` · `Overall Score` · `Actions`

### Reading
- **Cadence is quarterly** (`Quarter` column).
- **Eight scored dimensions**: Quantity of Work, Quality of Work, Consistency,
  Mentoring Peers, Team Player, Pro-activeness, Conduct, Credit Score.
- Three derived values: `Overall Percentage`, `Overall Score`, `Rank`.
- `Rank` implies **ordering across employees** — a cohort comparison, not an
  isolated score. Scope of the cohort (org / department / branch) is ⬜ unknown.

> The eight dimensions look like a **fixed** rating template here, but
> `Performance Review → Appraisal Templates` exists as a separate page — so the
> dimensions are probably configurable, and this is one template rendered wide.
> Model as `template → criteria → ratings`, never as eight hard columns.
> ⬜ Confirm against Appraisal Templates before building.

Value shapes (out of 5? out of 10? weighted?) are ⬜ unknown — empty state.

### Structure

Attachments hang off the **line**, not the claim.

> **⚠ Flag: `Expense Type` is a creatable combobox.** Free-typing a type means
> the master fills with "Travel", "travel", "Travelling", "Trvl" and every
> expense report becomes unusable. In ours this should be a strict FK to an
> expense-type master, with adding a new type an admin action. If users genuinely
> need ad-hoc types, add an explicit `Other` type plus a free-text note field —
> not a self-polluting list.

Currency: **₹ INR** — confirms the India-first assumption.

## 7. ⚠ Impact on our existing ATS codebase

`lib/types.ts:1` currently declares:

```ts
export type Role = "admin" | "hr_manager" | "recruiter" | "hod" | "candidate";
```

**There is no `employee` role.** The entire Me module assumes every employee has
a login and sees only their own record. That is a different authorisation shape
from the ATS's — where a handful of staff see everything and candidates see nothing.

This needs deciding at foundation time, not later:
- Does `profiles` (auth identity) stay separate from `employees` (HR record),
  joined by `profiles.id ↔ employees.user_id`? **Recommended** — an employee may
  exist before they have a login, and a login may exist without an employee record
  (external recruiters already do exactly this).
- Row-level security changes from role-based to **subject-based**: "rows where
  `employee_id = me`, or where I am in the requester's manager chain, or I am HR."
